# 本地测试与页面数据一致性

更新日期：2026-10-28。

开发先在本机验证，全部通过后再安排 MetaMask 和 Sepolia 验收。以下自动测试不会向 Sepolia 发交易，不消耗 Sepolia 测试 ETH，也不读取 `.env.sepolia`。本地 Hardhat 交易使用临时开发账户和本地测试币。

## 1. 怎么运行

通用部署入口另有专门的 `npm run test:deploy`，包含独立 31338 测试链与浏览器钱包适配器的公共流程检查，以及模拟响应的 Sepolia 页面检查，验证钱包拒签、部署回执、重复请求、刷新恢复和失败后重试。运行方式及真实 MetaMask 人工检查见[Sepolia 合约部署工作台](合约部署工作台.md)。NFT 成品图的固定公开链接与元数据已接入，真实钱包展示待 Sepolia 业务部署后验收；充值暂缓。图片验收见[素材说明](../assets/NFT_Pic/README.md)。

首次拉取代码先运行 `npm ci`，并按项目 README 安装 Python 依赖。浏览器测试默认使用本机 Google Chrome；没有 Chrome 时可运行 `npx playwright install chromium`，然后使用 `FORGE_TEST_CHROMIUM=1 npm run test:browser`。

在项目根目录运行：

| 命令 | 检查范围 |
|---|---|
| `npm run test:backend` | 游戏规则、账号、数据库事务、仓库存取和并发选择、旧字段迁移、网络隔离、链上只读接口和账号核对 |
| `npm run test:deploy:service` | 模拟 Sepolia RPC，验证最终确认、失败重试、记录恢复和连接错误，不发送链上交易 |
| `npm run test:deploy` | 6 项公共部署流程与 2 项 Sepolia 页面检查，不连接真实钱包扩展 |
| `npm run test:contracts` | 临时 Hardhat 上的 NFT 铸造、授权、挂牌、成交、提现、转移和失败条件 |
| `npm run test:i18n -w frontend` | 中英文文字、源码缺漏、金额、武器名称与确认框 |
| `npm run build` | 前端类型检查及生产构建 |
| `npm run verify:game` | 隔离闭环：真实本地合约、FastAPI、SQLite、三种 NFT 图片元数据和两钱包交易，再重启后端核对存档 |
| `npm run test:browser` | Chrome 实际操作页面，同时比较页面、HTTP 接口和 SQLite 中的数据 |
| `npm run test:browser -- --headed` | 同一批浏览器检查，显示浏览器窗口以便观察 |
| `npm run test:browser:report` | 打开最近一次浏览器测试报告 |

不需要先启动 `npm start`。浏览器测试和原有闭环各自新建数据目录、独立端口和进程，结束后停止自己创建的服务。自动测试不复用正在玩的后端或数据库。

## 2. 页面与数据库测试覆盖

本节的链下游戏浏览器检查运行真实 React/Three.js 页面，连接真实 FastAPI 和 SQLite。仅在异常测试中延迟或丢弃真实响应；不会用一套固定的假余额替代服务器。

| 场景 | 核对内容 |
|---|---|
| 注册、每日领取与刷新 | 账号归属、材料、保护符、金币、三把剑的额度、刷新后的存档 |
| 加热、取回、敲击 | 等待加热、取回铁砧、材料扣除、热量、等级和免损毁保护 |
| 商店、回收、取消确认 | 金币和材料变化、背包数量、回收估值、取消不写库 |
| 选路线和封存 | 服务器固定路线、封存状态、不可继续回收或修改 |
| 连续点击 | 一次动作只扣一次资源 |
| 成功响应丢失 | 服务器已经扣款后丢弃回复，前端使用原请求标识重试，不重复消费 |
| 旧刷新回复迟到 | 较早余额不能覆盖刚完成的购买结果 |
| 双标签页回收 | 一个页面回收后，另一个页面的旧操作失败并更新背包，不重复发币 |
| 双标签页换账号 | 页面身份和余额一起更新；旧页面不能替新账号提交消费 |
| 断网、后端重启、重新登录 | 不伪造扣费或新增武器，连接恢复后与原存档一致 |
| 会话过期与迟到的错误 | 清除过期操作入口；旧请求的错误不能清掉刚恢复的新登录 |
| 手机尺寸与语言切换 | 保持同一份余额和武器数据，检查页面横向溢出 |
| 存入 A、取出 B、刷新与重启 | 工坊取用状态持久化；存入后保持空闲，不自动挑下一把；等级、热量和保护进度不变 |
| 加热期间存取 | 取出后继续等待原定加热完成时间，不重扣材料，也不能提前敲击 |
| 数据库直接删除武器 | 在铁砧、手持、熔炉、展示柜四种位置分别删除；等待实际轮询后模型消失，不能继续敲击 |
| 数据库修改状态或归属 | 封存、损毁、回收、转给其他玩家后清空旧选择；等级、路线、热量修改后显示最新数值 |
| 展示柜与仓库交换 | 删除柜中 A 不影响正在锻造的 B；A→B→A 不恢复过期的手持位置；空工坊可以重新取用 |
| 双标签页存取与迟到操作 | 另一页存入武器后，迟到的加热请求失败且不扣材料；后台版本核对阻止旧选择覆盖新选择 |
| 操作等待和断网 | 即使操作回复延迟，后台轮询仍能清掉被删除的武器；断网隐藏旧模型，恢复后按数据库显示 |
| 场景内仓库面板 | 展开场景内直接存取，不跳页面；列表实时清掉删除项、禁用封存项，并显示取出失败原因 |
| 第一人称仓库交互 | 通过实际 WASD 走近木箱，按 E 打开；面板打开后释放鼠标并暂停操控，Esc 关闭后保持暂停 |
| 手机仓库与键盘焦点 | 英文窄屏存取、图片加载、无横向溢出；键盘焦点保持在打开的仓库面板中 |

链下操作成功后重新读取状态（敲击保留落锤动画的短暂反馈）；前台页面每 5 秒发起一次状态查询，窗口重新获得焦点时也会查询。它是轮询同步，不是 WebSocket 推送；隐藏的标签页恢复可见后查询。同步失败时标记“上次保存的数据”、暂停操作并隐藏旧武器模型，恢复后自动更新。操作请求带当前页面的玩家标识，后台与当前会话核对，避免其他标签页换账号后误扣余额。

数据库在 `players.workshop_weapon_id` 保存当前取用武器，`workshop_revision` 记录选择的版本。存入和取出接口同时核对版本，成功后在一个事务内更新；加热、敲击核对当前取用武器及前端提交的版本。`GET /api/state` 会清理失效的武器引用。客户端以武器 ID 和服务端选择版本识别当前武器，不再自动取数组第一项，也不在接口确认前切换模型。展示柜摆放只在当前场景中保留，每次绘制都按有效武器清理。

后端测试另覆盖真实并发存取、旧数据库迁移、重启恢复、钱包绑定迁移工坊选择、存入后又取出同一把时拒绝旧加热请求。自动测试对数据库的删除、改归属仅发生在临时测试存档中。

### 手动试玩仓库

1. 运行 `npm start`，登录后领取两把基础剑；旧存档可直接从仓库取出已有武器。
2. 给 A 加热并敲击，记住等级和剩余热量，再点锻造画面上方“存入仓库”。应看到“工坊空闲”，加热、敲击不可用。
3. 打开武器仓库，对 B 点“取出并继续锻造”；B 应出现在铁砧上。再次取出 A，核对原有进度。
4. 分别在有武器和空闲状态刷新页面，两种状态都应保留。也可开两个标签页存取，另一个页面会在下一次成功同步时更新。
5. 点击三维画面顶部“仓库”，在弹出面板中重复存入和取出；展开场景后也可用，不应跳出游玩界面。取出后点击“继续锻造”或“返回游玩”。
6. 第一人称走近左墙边“武器仓库”木箱，按 E 打开；鼠标应释放、移动和敲击暂停。Esc 关闭面板，再点击三维画面恢复操控。环绕模式也可直接点击木箱。

存取不扣资源，不需 MetaMask，不消耗测试 ETH。首次升级旧存档时工坊为空属于预期，不代表武器丢失。破坏性异常检查使用 `npm run test:browser`，无需手动改日常游戏数据库。

## 3. 数据与报告在哪里

- 浏览器数据与服务日志：每次自动生成 `.local/browser-tests-*/`，数据库是该目录下的 `game.sqlite3`。
- 本地链闭环数据与报告：`.local/verify-game-*/verification.json`。
- 浏览器报告：`playwright-report/`；失败截图、追踪和数据库摘要：`test-results/`。这些目录由 Git 忽略，不提交当前存档或测试账号资料。
- 后端单元测试连模块初始化也使用临时目录；不会为了导入测试代码而打开日常游戏存档。

测试账号由脚本在隔离数据库中创建，需要时赋予测试角色。不要将脚本中的测试密码用作日常账号密码。报告保留用于定位失败；需要清理时仅删除对应测试目录，不删除 `.local/` 整体。

## 4. 当前边界和之后的人工验收

浏览器套件覆盖链下游玩与数据同步；本地链交易由 `verify:game` 使用软件钱包验证。真实 MetaMask 的弹窗、拒签、切换网络/账号、交易替换仍需要人工验证。充值、质押和资金结算尚未实现；NFT 独立监听及停机补扫已另外完成本地验证，不能把现有测试通过当作这些功能已经验收。

后续每加入一条链路，先扩展这里的本地检查。需要人工测试时，提供明确的前置条件、使用钱包、点击步骤、预期余额/归属变化和失败判据；再安排少量 Sepolia 交易核验。充值比例、质押产币速度、离线累计和取回规则在实现前按功能计划确认。
