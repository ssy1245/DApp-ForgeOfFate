# 奖励邮箱

[返回项目 README](../README.md#奖励邮箱)

## 当前行为

- 游戏侧栏显示待领取数量，未读邮件使用醒目数字；其他游戏页面显示可点击提醒，每次状态同步更新，全部领取后消失。
- 收件箱按奖励日期倒序分页。点击邮件仅标记已读，单封领取或一键收取才加游戏金币。领取完成后邮件移出列表；未领取邮件保留，不自动过期。
- 一键收取包括未读邮件和其他分页。金币、领取流水、邮件状态和请求响应一起提交；任何一步失败全部回滚，不出现邮件消失但奖励没到账。
- 邮箱属于游戏账号，和浏览器钱包是否连接无关。后续真实质押奖励仍须先由质押人已验证的钱包关联到账号。
- 测试模式 + `tester` 账号可在邮箱底部生成测试邮件，单封 1–1,000,000 金币，类型为 `test`；生成时不增加余额，正常账号不能使用。重复点击一次未完成操作或网络重试不重复发信，之后主动再次生成则是新的测试邮件。

**质押合约、RPC 事件解码和奖励结算引擎已实现，本地完整演练通过；尚未部署到 Sepolia。** 现有监听每轮会处理已登记来源的结算和待投递奖励；当前没有真实质押来源，因此不会凭 NFT 持有记录自动产币。

## 接口与权限

| 接口 | 行为 |
|---|---|
| `GET /api/mail?offset=0&limit=30` | 当前账号未领取邮件、未读/待领取数及附件金币合计；`Cache-Control: no-store` |
| `POST /api/mail/{id}/read` | 仅标记自己的邮件已读，不加金币 |
| `POST /api/mail/{id}/claim` | 领取自己的单封邮件；已领邮件再次请求不再加币 |
| `POST /api/mail/claim-all` | 领取当前账号全部待领取邮件，不限当前分页 |
| `POST /api/cheats/mail` | 仅测试模式的测试账号；为自己生成带 DEMO 标记的测试奖励邮件 |

写请求沿用 `Idempotency-Key` 和 `X-Forge-Player`。后者核对浏览器当前档案，防止另一标签页换号后把旧操作落到新账号。同一请求键重试返回原结果，不包含请求完成后新到的邮件；其他账号无法查看、读取或领取指定邮件。没有公开的真实奖励发件接口，领取金额只从服务器保存的附件读取。

## 质押结算规则（已实现）

按用户确认的 **UTC 日历日、实际有效秒数折算**。每个仓位保存每日费率，公式为：

`本日整数金币, 余数 = divmod(本日有效秒数 × 每日金币 + 上次余数, 86400)`

- 例：每日 100 金币，10 月 1 日 12:00 UTC 质押，10 月 3 日 12:00 UTC 取回，分别产生 50、100、50 金币三封日奖励邮件；停机后补扫也得到同样结果。
- 每个仓位的余数跨日保留，不受重启或结算频率影响。游戏只使用整数金币；仓位结束后不足一金币的余数保留供审计，不支付、不合并到另一个仓位。重新质押使用新仓位身份。
- 同一钱包同一天多个仓位的整数奖励汇总为一封邮件。结果为零时不发空邮件；完整 UTC 日结束且对应链上历史已最终确认后才投递，不实时按秒入账。UTC 零点为北京时间 08:00，还需等待链上最终确认。
- 离线时间正常累计，但只计算到链上的实际取回时间。系统时间、玩家提供的时长、当前 NFT 持有人均不作为收益依据。
- 每次最多结算 30 天，长时间离线分批追赶。扫描、结算和领取分别保存进度；正常账号请求可在追赶批次之间执行。
- 无已验证账号的钱包先保留每日奖励；之后完成验签绑定，再自动投递。无需重新扫描历史，也不会因早先没绑定丢失收益。

每日金额配置为 `.env.sepolia` 的 `FORGE_STAKING_COINS_PER_DAY`。默认 `0` 表示未配置，不允许登记奖励来源，不是免费率仓位。实际数额仍需确定。首次登记时冻结来源费率，新仓位保存快照；修改配置不会重新定价旧记录，冲突直接报错。当前未提供运行期间调价功能；未来如需调价，须新增明确生效边界和规则版本，不能清除旧数据或伪造新部署。

## 接入真实质押监听

实现位于 [staking_rewards.py](../backend/staking_rewards.py)，都是可信服务端函数，没有开放给玩家的发件或仓位写入 API。

1. 部署 `ForgeStaking` 合约，工作台保存独立清单；监听会将已验明的链 ID、合约地址、部署身份和部署前一块的高度/哈希/时间传给 `register_source`。部署前的区块作为起点，避免漏掉部署区块内的事件。
2. `RpcStakingSource` 核验合约、最终确认边界、区块哈希与完整日志范围，将每段连续区块的 `stake` / `unstake` 事件交给 `apply_finalized_batch`。每次调用放进 `Store.connection()`，异常必须退出事务。事件字段包括 block、log_index、timestamp、position_id、wallet；stake 另含 token_id。timestamp 必须来自对应链上区块，wallet 必须来自质押事件记录的实际质押人。position_id 必须是每次锁仓独立的身份。
3. 完整解码并保存这一范围内所有事件后才推进该来源的边界；没有事件的区间也推进。输入重复批次返回原结果，冲突、缺段、未知取回、重复占用 NFT 均拒绝，不能跳过坏记录继续。
4. 生产监听的 `chain.server.indexer.Indexer.tick()` 已在 NFT 事件处理后调用 `StakingIndexer.tick()`，先核验并补齐质押事件，再调用 `settle_source`。仅使用结算引擎的测试仍可调用 `settle_all(store)`。结算只采用各质押来源自己已完整处理的最终确认边界，不能借用 NFT 监听高度、最新区块高度或服务器当前时间。
5. `settle_source` 在同一个事务内更新仓位余数、历史累计、结算日期、最后结算产奖时间，创建每日奖励，并调用 `deliver_reward` 发邮件。失败整体回滚。未绑定钱包的持久奖励是待投递账目，绑定后投递和关联邮件也同事务提交。

`staking_sources.last_reward_at` / `staking_positions.last_reward_at` 是最近一次计算出非零整数奖励的服务器时间；`settled_until` 是已结算的链上时间边界，补发从此处继续，不能拿服务器发信时间作为计息起点。`reward_mail.created_at` 则记录实际投递时间，领取时间另存。

同一账号、类型、来源、日期只存在一封邮件。重复结算金额相同返回原邮件 ID；金额不一致直接报冲突，不修改旧奖励。已领取的邮件仍保留唯一身份，不能因为前端删除而再次发放。来源身份包含链 ID、合约地址与部署身份，进度不能在不同部署间复用。

**目前不能仅填写费率就产生真实质押收益。** 合约与事件解码已经实现，但仍需通过质押部署工作台部署到 Sepolia、配置费率，并实际质押 NFT。NFT 的 Transfer 事件不会被当作质押。已用独立本地链完成真实合约→RPC→停机补发→邮件领取演练，步骤见[质押合约](质押合约.md)。

## 入账与保留记录

`reward_mail` 保留附件、已读和领取时间；`reward_mail_claims` 以邮件 ID 为主键，保存实际金币和领取前后余额。玩家看到的“删除”是领取后移出收件箱，后台不删除去重凭据。这些表随游戏数据库备份，重启不会清空。

现有游戏余额使用整数并通过 JavaScript number 传输。邮箱不允许入账突破 `2^53−1` 的精确整数范围：此时整次领取失败、所有未领取邮件保留，不截断、不丢弃余额。附件合计以十进制字符串传输并在前端精确显示。后续真正不限累计的长期质押方案，仍需要按开发计划统一金额精度和完整游戏币账本；本表仅覆盖邮件奖励。

## 成交通知

`notice_mail` 与奖励附件独立，合并到同一收件箱和未读提示。`trade_sold` 邮件展示交易成功、NFT 编号、买家、以字符串保存的 Wei 金额及交易哈希。阅读仅标记已读；`POST /api/mail/{id}/dismiss` 归档通知，不修改金币。一键收取仅领取奖励邮件，不清除通知。

`market_sales` 以已确认事件的 `(block_hash, log_index)` 为唯一键。监听在同一数据库事务内将卖家封存武器设为 `sold`、创建唯一通知和写入投递标记；失败整体回滚。没有验证钱包绑定时保留待投递记录，绑定后再次处理。新版本还会补处理历史 `Purchased`，删除通知后仍保留唯一记录，避免复活邮件。每个数据库已绑定网络、合约与部署身份，不跨环境复用事件。普通 `Transfer`、挂牌、撤单均不触发成交邮件。

成交款由原 NFT 合约记入卖家可提取收益，邮件不转账也不发放游戏金币。原始链上资产和后台审计记录保留，玩家界面移除的是卖家已售卡片。测试入口：`backend/tests/test_market_sales.py`。
