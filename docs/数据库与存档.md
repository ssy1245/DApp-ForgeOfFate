# 账号、数据库与存档维护

[返回项目总 README](../README.md)

本文保存表结构、账号权限与备份操作细节。真实游戏存档不得用于自动化回归。

## 账号、数据库与发剑规则

### 当前已实现

- **账号与登录**：支持用户名（3–24 位中文、字母、数字或下划线）和密码（8–128 位）注册 / 登录 / 退出。用户名忽略英文大小写；密码使用随机盐与 PBKDF2-SHA256（600,000 次）单向哈希保存，不存明文。会话令牌仅保存哈希，浏览器使用 HttpOnly、SameSite=Lax Cookie。
- **存档归属**：首次打开创建临时档案；直接注册会保留当前剑、资源和进度。登录已有账号会切换至该账号档案，不会合并当前临时档案。退出后进入新的临时档案；重新登录恢复原账号。普通游戏不需要钱包。
- **数据库内容**：`accounts` 存账号 ID、用户名、密码哈希、角色、游戏档案关联与注册时间；`players` 存材料、保护符、金币、每日领取日期及已领剑数量；`weapons` 存归属、品质、来源、等级、状态、热量与强化 / 保护进度；`sessions` 存会话，`wallet_bindings` / `wallet_challenges` 存钱包关系与一次性验证挑战；`operations` 保存幂等请求结果。已有数据库启动时自动补充新字段，无需清空。
- **每天三把基础剑**：工坊左侧靠入口增加实体领剑架及数量牌，显示“今日可领 N / 3 把”。第一人称靠近按 E，或环绕模式点击剑架 / 按钮，通过 `POST /api/supply/sword` 每次领取一把 **+0 普通剑**（`source=daily`），无需材料、金币或钱包；工坊空闲时自动取用，已有武器时只收入仓库。读取状态不再自动发剑；领取额度按 UTC 日期计算，未领额度不跨天累积，已有武器保留。`players.sword_day` 与 `daily_swords_claimed` 保存领取进度，重复请求、并发、重登和钱包绑定不重复增加额度。旧存档已有 `sword_day` 的日期按已领完原三把处理，避免迁移后重复发放。数量牌及界面随领取更新，跨天、重新切回窗口及多标签页操作后自动同步。每日材料 / 保护符仍由“领取每日补给”单独领取。
- **测试补领**：仅 `DEMO_MODE=1` 开放。当今日三把剑已领完且背包没有任何可强化的剑时，页面显示“领取一把普通测试剑”。点击免费发放一把 +0 普通剑，保留 DEMO 来源标记，并把铁块至少补足到 20，避免刚领就无法加热。背包仍有可用剑时不能补领；只有封存收藏品也可以补领。敲坏后可继续领取，不是正式经济系统的无限发剑规则。
- **游戏币买剑**：页面底部用 **2,500 游戏金币购买一把 +0 普通剑**（`source=coin_shop`），与每日领取及铁块锻造的剑使用相同的初始等级、品质和强化规则。金币扣除与发剑在一个数据库事务内完成，重复请求不会重复扣款。与系统回收、材料购买构成链下循环，不需要钱包。
- **降低损毁率**：普通无保护阶段损毁率为 `min(1% + 等级 × 0.2%, 15%)`：+0 为 1%、+10 为 3%、+50 为 11%。保护符 / 阶段保护仍将损毁转换为等级不变。展示概率和实际后端结算来自同一配置。

当前是本地测试账号系统；邮箱验证、找回密码、登录限流和正式部署的 HTTPS 会话配置尚未实现。临时档案依赖浏览器 Cookie；需要跨浏览器恢复时应先注册账号。

### 普通账号与测试账号

先启动 Sepolia 测试模式 `npm run start:demo`，再运行 `npm run accounts:setup` 在 `.local/sepolia/` 准备本机测试账号。默认只创建 `forge_test`；当前自测使用已绑定项目负责人钱包的这个账号，角色 `tester` 持久保存在数据库中。

| 账号 | 类型 | 权限 |
|---|---|---|
| `forge_test` | 测试账号（`tester`） | 正常游戏 + 作弊菜单，可反复刷剑和资源 |
| `forge_player`（可选） | 普通账号（`player`） | 仅显式运行 `npm run accounts:setup -- --with-player` 时创建，用于单独验证普通玩法 |

运行 `npm run accounts:setup` 后，初始密码说明生成在本机 `.local/sepolia/test-accounts.md`；该文件不纳入 Git，尚未运行设置脚本时不存在。账号是本地开发用固定凭据，不是正式服务的默认账号。设置脚本重复执行不会重置已有账号的密码、权限或进度。

当前演示账号供项目负责人自行操作和录制，老师通过演示与链上记录验收。钱包绑定保留既有签名验证结果，不在源码中硬编码钱包归属，也不分发当前数据库或钱包密钥。新环境自行创建账号后，仍须用实际钱包签名完成绑定。

页面右上角“账号登录 / 注册”使用用户名密码登录。新注册的账号与已有账号迁移后默认均为 `player`，注册请求不能自行指定测试权限；接口中的 `guest` 兼容字段表示尚无已验证的钱包，不是账号类型；钱包状态使用 `wallet_address` 和 `wallet_verified`。退出后再登录另一个账号切换存档。

测试账号登录后显示“作弊菜单”：

- **无限补给**：反复添加三把基础剑和一份每日材料 / 保护符，不影响正常每日领取日期。
- **资源**：自选材料、保护符、金币或全部，每次添加 1–1,000,000；单类资源暂定上限十亿。
- **批量刷剑**：选择普通 / 精良品质、+0 至 +90（新剑默认骑士剑路线）、每批 1–100 把，可无限次执行，不扣资源。
- **当前剑**：调整等级、立即烧红补足五锤、耗尽热量、免损毁 100 锤或移除保护。仅能操作自己未封存的剑，封存后的属性仍固定。

作弊生成或修改的剑保留 `DEMO` 标记与 `source=cheat`，操作使用同一套事务和幂等记录。后端每次检查 **DEMO 模式已开启 + 当前账号角色为 tester**；普通账号、临时档案和未登录请求均不能调用作弊接口。普通运行模式即使登录测试账号也不开放作弊菜单。原来的“没剑时补一把”仍按现有测试环境规则开放，和测试账号的无限刷取区分。

测试接口为 `POST /api/cheats/daily`、`/api/cheats/resources`、`/api/cheats/weapons`、`/api/cheats/weapons/{id}`。账号的角色由本地设置脚本 / 数据库维护，没有公开提权接口。


## 数据库与存档说明

### 当前实际使用的数据库

- **引擎**：SQLite，通过 Python 标准库 `sqlite3` 直接访问，没有 ORM。此次检查运行库版本为 **3.50.4**，写前日志模式为 **WAL**。
- **文件**：日常 Sepolia 环境为 `.local/sepolia/game.sqlite3`；旧本地环境 `.local/game.sqlite3` 保留，二者独立，不自动迁移账号与武器。
- **连接**：后端直接打开本地文件，不需要数据库账号、密码、连接 URL 或单独启动数据库进程。普通启动自动建库 / 建表；测试通过 `create_app(db_path=...)` 使用临时数据库，和当前游戏存档隔离。
- **事务**：每次连接使用 `BEGIN IMMEDIATE`，资源扣除、武器变化和请求记录在同一事务中提交，失败回滚；等待写锁超时为 15 秒。当前读操作也使用这一连接方式，适合现阶段本机规模，后续需优化并发。
- **检查结果**：2026-10-26 只读检查 `PRAGMA integrity_check` 返回 `ok`。这表示文件结构检查正常，不代表订单监听、业务审计等后续功能已经实现。

### 游戏核心表、钱包关联与链上索引

| 表 | 保存内容 | 当前关联 / 约束 |
|---|---|---|
| `accounts` | 用户 ID、用户名、密码哈希、`role`、游戏档案关联、注册时间 | ID 主键；用户名和 `game_address` 分别唯一；角色默认 `player` |
| `players` | 材料、保护符、金币、每日资源 / 赠剑日期、临时档案标记、`workshop_weapon_id` 与 `workshop_revision` | `address` 主键；当前也是其他表引用的游戏档案标识 |
| `weapons` | 武器 ID、归属、等级、普通 / 精良品质、来源、状态、普通锤数、保护次数、加热就绪时间和剩余热量 | ID 主键；`owner` 逻辑关联 `players.address` |
| `sessions` | 会话令牌的 SHA-256 哈希、游戏档案、过期时间 | 哈希主键；不保存明文 Cookie 令牌 |
| `challenges` | 旧版钱包登录挑战，保留历史结构 | 旧接口已停用，不能再消费 |
| `wallet_bindings` | 账号与钱包的一对一关联、验证时间 | 账号主键；钱包地址不区分大小写唯一；验证时间为空表示旧关联待重验 |
| `wallet_challenges` | 账号、会话哈希、目标钱包、网站、网络、原始消息与到期时间 | 一次性随机码主键；成功消费后删除 |
| `operations` | 档案、请求标识、操作指纹、返回结果 | `(address, key)` 联合主键；防止重试重复扣资源 / 发剑 |

此外已建立 `runtime_environment` 网络隔离表、`schema_migrations` 迁移记录，以及 NFT 部署、扫描、区块检查点、事件和归属索引表，详见[链上监听与恢复](../chain/链上监听与恢复.md)。

上述游戏核心表的 `accounts.game_address`、`sessions.address`、`weapons.owner` 等关联目前由应用代码维护，**尚未声明数据库外键**。游戏核心表尚未增加归属、状态、过期时间等专用查询索引；链上事件表已有待处理事件索引。

武器状态为 `active`（可强化）、`sealed`（封存）、`destroyed`（损毁）或 `recycled`（回收）。损毁 / 回收后仍保留数据库记录，背包过滤隐藏。来源已有 `forge`、`daily`、`coin_shop`、`test_supply`、`cheat`。未来若做充值，建议只增加游戏币；当前没有充值入口。

### 链下存档与链上归属

账号、资源、普通剑、加热、强化、每日领取和作弊记录存在 SQLite；已铸造 NFT 的持有人、挂牌价格、成交与待提取收益以合约为准。市场最新状态通过后端查询合约；独立监听将确认后的 NFT 归属、挂牌和事件历史保存到 SQLite。卖家提现无合约事件，尚不属于历史索引范围。

`players.address` 是内部存档标识，即使形式像地址也不表示玩家控制该钱包。固定玩家 ID 使用 `accounts.id`；绑定只更新独立的 `wallet_bindings`，不改 `players.address`、账号关联或武器归属。历史钱包地址形式的存档键原样保留，链上操作必须另外检查绑定关系与签名验证状态。

### 数据结构升级与备份

- 旧游戏表通过启动时建表和逐列补字段兼容升级，保留已有数据；工坊取用状态的旧库升级已有测试。新增链上结构通过 `schema_migrations` 记录 `chain-index-v1`，已验证迁移及事务处理；覆盖整个游戏库的统一版本迁移和回滚 / 恢复流程仍待完成。
- 活跃数据库可能同时存在 `game.sqlite3-wal`、`game.sqlite3-shm`。**不要仅复制正在运行的主文件作为完整备份**；使用 SQLite 在线备份接口，或停止所有写入并完成日志检查点后再复制。
- 以下命令从项目根目录执行，使用 SQLite 在线备份接口生成独立快照；备份也在 `.local/` 内，不纳入 Git：

```sh
.venv/bin/python - <<'PYBACKUP'
from datetime import datetime, timezone
from pathlib import Path
import sqlite3
source = Path('.local/sepolia/game.sqlite3').resolve()
folder = Path('.local/sepolia/backups')
folder.mkdir(parents=True, exist_ok=True)
name = datetime.now(timezone.utc).strftime('game-%Y%m%dT%H%M%S%fZ.sqlite3')
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as src:
    with sqlite3.connect(folder / name) as dst:
        src.backup(dst)
        assert dst.execute('PRAGMA integrity_check').fetchone()[0] == 'ok'
print(folder / name)
PYBACKUP
```

恢复前先停止后端及所有数据库写入脚本，并保留当前库的快照；将备份先恢复到临时位置，检查完整性及登录 / 背包 / 资源后，再替换游戏库并重启后端。不要手工删除正在使用的 WAL / SHM 文件。定时备份、备份保留策略和完整恢复演练仍在待办中。

## 数据、凭据与恢复

- `.local/sepolia/game.sqlite3`：当前账号、游戏状态、会话和操作记录；SQLite 事务和请求标识防重复结算。
- `.local/sepolia/deploy-console/forge-of-fate/`：NFT / 市场的固定计划、编译资料、交易状态和核验记录。
- `.local/sepolia/deploy-console/deployment-probe/`：可选验证合约的独立记录；通过 `npm run deploy:console -- --module deployment-probe` 继续原 Probe 计划。
- `.local/sepolia/mint-key`：服务器铸造授权密钥，首次准备 NFT 计划时生成，权限 0600；不是 MetaMask 私钥。已有计划缺失密钥时停止，需恢复原文件。
- `.local/sepolia/deployment.json`：NFT 最终确认后自动保存的版本 2 业务清单。之后重新启动游戏服务，启动器读取清单并启动监听；旧部署不覆盖。旧本地链资料仍留在 `.local/` 原位置。
- 普通游戏使用后端档案，浏览器通过 HttpOnly 会话 Cookie 恢复进度；材料、等级、加热和强化结果保存在 SQLite。无需钱包参与。
- 铭刻前先登录游戏账号并签名绑定钱包；绑定不搬动存档、不更换游戏会话，注册 / 密码登录会话有效期为 30 天。待确认链上交易保存在浏览器 localStorage，按网络、合约、部署标识、钱包隔离；刷新或重新打开同一浏览器可继续检查。清除站点数据会移除这些本地记录。
- 日常启动明确读取 `.env.sepolia`，数据库目录为 `.local/sepolia/`；`.env` 仍不自动读取。公开模板提供字段说明，私密 RPC 不发送给前端。
- `.local/`、`.env`、虚拟环境、数据库和构建产物已忽略。不要把本地密钥或日志纳入 Git。

Sepolia 合约在本机服务关闭后继续存在。重启工作台读取原部署计划与交易记录，重启后端读取该网络的存档；保存整个 `.local/sepolia/` 目录。旧本地链属于历史开发环境，停止后其内存链状态不会迁到 Sepolia；旧磁盘存档保留。

现有 NFT 等级与元数据在铸造后固定，`tokenURI` 保存内嵌 JSON 的 data URI，新的 `image` 已使用公开图片仓库的固定版本地址。图片读取依赖托管地址，图片文件本身不存入链上；更新映射不会修改已有 NFT 或已签发的授权。概率与资产来源由后端背书，链上只验证铸造授权及归属交易。
